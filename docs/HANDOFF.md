- 형태: 독립 실행 + Claude Code 등 어디에나 연결.

## 지금까지의 결정
1. 구조: 헤드리스 코어 + 어댑터 층 + 도메인 팩.
   - 코어: 루프(모델 독립, 직접 작성, 범용 프레임워크 import 안 함), 정책 엔진(규칙을 프롬프트가 아니라 코드로 강제), 상태·이벤트 로그(세션 간 지속), eval 러너(ablation 포함).
   - 어댑터: inside(Claude Code hook·플러그인·MCP), beside(단독 CLI + ACP), above(다른 에이전트 감싸기. Databricks Omnigent와 겹치므로 마지막).
   - 정책·skill·상태는 하네스 중립 형식으로 한 곳에 둔다. AGENTS.md/SKILL.md/MCP 등 호스트 형식으로 변환한다.
2. 근거 요약 (출처 재확인 필요):
   - 상용 코딩 하네스 11개 분석에서 범용 프레임워크를 import한 곳 없음.
   - 같은 모델도 하네스만 바꾸면 성능 차이가 크다.
   - 공개 CLAUDE.md 보안 규칙 중 실제 통제로 뒷받침되는 것은 4.4%.
   - 하네스의 60%는 테스트/eval이 없다.
3. 온톨로지 팩 (데이터셋 → 온톨로지 + 사용자 질의):
   - 프로파일링(결정적 코드) → 목적 질의 1회(템플릿, CQ 초안) → CQ별 독립 초안(OWL + 선언적 매핑) → 불확실성 원장 → 검증(OWL 추론, SHACL, CQ→SPARQL 실행, 미사용 요소 표시) → 반복.
   - 불확실성 원장: 결정마다 후보·근거·신뢰도·영향을 기록한다. `(불확실성×영향) − 질문비용` 기준으로만 질문한다. 묻지 않은 결정은 "가정"으로 표시한다.
   - 관계형 DB는 NVIDIA Auto Ontology(2026-11 공개, Apache 2.0, MCP 읽기 전용 도구 9개, `check_answerable`)를 하위 엔진으로 쓴다.
     한계: 정확도 수치 미공개, 구축 단계 질의 우선순위 없음, 내부 포트 인증 없음, 외부 기여 불가.
   - 우리 차별점: 구축 단계 불확실성 원장 + 질문 우선순위(EVPI 방식).
4. FDE 하네스 5단계:
   - P1 투입: 상황 인식 맵(실제 흐름, 시스템·데이터 이동, 수작업 단계, 결정 지점, 이해관계) 초안 + 현장 확인 질문 목록.
   - P2 발견: 문제 후보 점수화, eval 먼저, 실제 데이터 연결(온톨로지 팩), 2주 내 데모. 게이트: "가장 가치 있는 일인가".
   - P3 채택: 1주 내 작은 성과 후보 추출, 사용 로그.
   - P4 경제성: 철수 조건을 코드 정책으로 둔다(소규모 계약, 정치적 장애, 챔피언 부재, 막연한 검증 요구).
   - P5 인수인계: 시스템 + eval + runbook + 챔피언 자료 자동 생성. 필드 패턴 라이브러리에 축적.
   - 자동화 안 함: 현장 관찰, 신뢰 형성.
   - Engagement 상태(상황 맵, 가정 원장, 결정 기록, eval, 산출물)가 단일 진실 원천이다. 게이트 = 정책 엔진.
   - 고객 보안 제약 때문에 온프레미스 모델·단독 모드가 필수이다. → 로컬 LLM: `docs/LOCAL_LLM.md`.
5. MVP: 한 업종의 데이터 분석·리포팅 업무. P2 + P5부터.
